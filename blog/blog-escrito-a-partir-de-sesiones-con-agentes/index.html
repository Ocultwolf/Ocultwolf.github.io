A blog written from my agent sessions (and why the first version was useless)

How I turn hundreds of agent sessions into articles: why the automatic journal didn't work, how I verify every fact, how I made the texts sound like me, and how I keep a secret from slipping out.

Craft · this blogBack to blog

This blog is largely written by agents that read my work sessions with other agents. It sounds like a recursive joke, but there's a very concrete problem behind it: I spend all day working with Claude Code, Codex and my own agents, and everything I learn ends up buried in hundreds of conversations. In this chapter I explain how I built the system that turns that into articles, and why the first version produced entries that were useless to anyone. I also cover the three pieces that fixed it: verified sources, a filter with my voice, and a detector for sensitive data.

The first version: an automatic diary

The initial idea was an agent that would read what I had worked on each day every night and publish one entry per project. It's a Django command that runs from cron at 23:30:

  1. Collects the day's messages from three sources: Claude Code sessions, Codex sessions and the OpenClaw command log. It groups them by piece of work: each named session is its own group, and automatic runs are grouped by project.
  2. Filters out the noise ("hi", "ok", tests, lost sessions) and redacts keys, tokens and pasted text.
  3. Summarizes into a bounded digest: at most 12 snippets per group and 320 characters per snippet. The model never receives the whole session.
  4. Generates the entry with claude -p. The prompt forbids paths, ports, service names, internal URLs and any infrastructure detail, and it requires returning skip if there's no real work to talk about.
  5. Retries once if the model discards. It isn't deterministic, and a second attempt keeps me from losing real work to a random discard.
  6. Doesn't duplicate: each entry carries a source key (project and day), so if I run the command twice it doesn't publish twice.

Security-wise it was well thought out. In one month it published 23 entries and discarded 17.

Why it wasn't good enough

The entries were correct, but they gave whoever read them very little. They were a diary of "this week I was working on...", with strategies and thoughts mixed together and sorted by date, not by topic. When I reviewed the system to rebuild it, the cause became very clear: the generator only saw what I asked for, never what happened. The digest was my messages, truncated. It didn't include the agents' replies, the code, the commits or the test results. With that you can only write a vague narrative of intentions.

The best example is in the sync's own log. On September 22 it discarded an entry with this reason: "the evidence only describes an operational problem (excessive API spending) and an audit request, with no real completed work to document". That day was the diagnosis of the 12-million-token incident, which became the chapter on cost. Read from my messages, it looked like a complaint. The real work was in the replies, in the logs and in the usage report, and the generator couldn't see them.

Lesson: what a model generates can't be better than what you give it to read. If it only sees the questions, it can't tell the answers.

The new version: chapters by topic, with verified sources

I changed the format and the sources at the same time. Instead of one entry per day, there are now chapters by technical topic, each self-contained, with this structure: problem, design, what failed, fix and lessons. And instead of a digest of my messages, each chapter is built from everything that leaves a real trace: commits with their messages, the current code, Saturno's task database, and the logs and agent replies in the sessions, which is where the diagnoses are. For now this isn't automatic: chapters are prepared in a dedicated session with an agent that goes through the sources one by one, and the nightly sync no longer publishes, it only leaves drafts to serve as material.

The most important rule: every fact is checked against the code or the source before it's published. Several chapters changed along the way because of it:

  • In the Saturno chapter, a code snippet that was illustrative in the draft turned out not to match what the real code does. I replaced it with the actual line.
  • In the cost chapter, the $2,400 figure that appeared in the code's own comments was a units error (cents read as dollars), and I checked it against the real balance.
  • In the concurrency chapter, when I checked the validations against the active branch I found they weren't there: they lived in a WIP commit on another branch. That ended up being an entire section of the chapter.

What can't be verified is stated as such: "most likely", "according to the comparison I did at the time", "it was never run again".

Lesson: a technical text generated with agents needs the same control as its code. Every claim has to be checked against something other than the model's memory.

Making it sound like me

The second problem was voice. The generated texts sounded like what they are: correct, neutral, with nobody behind them. I wanted them to sound like how I talk. With one catch: I write fast, with no accent marks, almost no commas and with spelling mistakes, and those do have to come out corrected.

Where my voice comes from

There was plenty of material, namely all my messages in the sessions. A script extracts them from three sources (Claude Code, Codex and what I've said by voice to Neon, already transcribed) and discards everything that isn't my voice:

  • the automatic prompts from Saturno and from the sync itself;
  • the commands, tests and terminal errors I paste;
  • the messages Neon forwards over the bridge, which are written in voseo and refer to "Pablo" in the third person;
  • and the texts I drafted with another AI and pasted afterwards.

That last filter has a trick. Those texts can be told apart because I don't use accent marks. If a message I typed has more than 3.5% of words with an accent mark or an ñ, I didn't write it. It isn't applied to transcribed voice, because the STT does add accent marks. In the end about 850 messages and 31,000 words were left.

def accent_rate(text: str) -> float:
    words = re.findall(r"\w+", text)
    return sum(bool(re.search("[áéíóúñ¿¡]", w)) for w in words) / max(len(words), 1)

typed_by_other = source != "neon_voz" and accent_rate(text) > 0.035

Prompt, not fine-tuning

I considered training a model, but ruled it out for three reasons. First, my messages are instructions to agents, not articles, and a model trained on them would learn to write "ok go on with that point". Second, it would also learn my spelling mistakes, unless I first corrected the whole corpus and built pairs of "neutral text → my text". And third, a small model trained locally writes technical content quite a bit worse than a large model that's well guided.

So the filter is a prompt with two pieces that I can read and edit. One is a voice profile: how I reason, which connectors I use and how sparingly, Spanish from Spain, and what I never do. The other is an example bank, with real messages of mine with spelling and punctuation corrected and not a single word changed.

What had to be adjusted

  • The first version was timid. With so many "keep the content" and "don't make things up" instructions, the model only fixed accent marks. I had to tell it explicitly to rewrite every sentence from scratch the way I'd say it, without removing the ban on adding facts.
  • Code can't go through the model. Code blocks are replaced with placeholders before calling the model and restored afterwards. If any placeholder is missing from the output, the filter fails instead of publishing a text with lost code.
  • It made up emotions. In one test it added "at first I didn't understand why", which wasn't in the original. Now I check every output with a word-by-word diff to see what it added.
  • Colloquialisms that aren't mine. In one chapter it slipped in expressions I don't use. The rule is now written into the profile: if it doesn't appear in my corpus, it doesn't go in.
def _protect_code(text):
    blocks = []
    def stash(m):
        blocks.append(m.group(0))
        return f"[[BLOQUE_CODIGO_{len(blocks) - 1}]]"
    return CODE_BLOCK.sub(stash, text), blocks

Lesson: to imitate a style, an explicit profile with real corrected examples works better than training on text that isn't the kind you want to produce. And the imitation has to be watched, because it tends to make things up and exaggerate.

Don't let anything leak

The third piece is the one I care about most. A work session ends up containing everything, keys and tokens included, so any chapter built from them is a leak risk. That's why there's a detector that looks for known key formats, long tokens, JWTs, IPs, emails, user paths, tunnel URLs, assignments of the KEY=value type and names of credential environment variables. There's also a command that checks all posts before publishing:

python manage.py audit_posts          # informa; sale con código 1 si hay algo pendiente
python manage.py audit_posts --fix    # sustituye lo encontrado por [censurado]

On its first pass it found, inside a code snippet, the names of the environment variables for a provider's key and voice ID. They weren't the values, but the rule is not to publish even that, and they now appear as [censurado]. The non-zero exit code is deliberate: that way the check blocks publication instead of staying a suggestion.

Lesson: when the raw material contains secrets, redaction can't depend on me remembering. It has to be an automatic step that fails explicitly if it finds something.

What I take away

  1. The model can only tell what it reads. Give it the results, not just the questions.
  2. Organize by topic, not by date. A diary serves whoever writes it; a chapter serves whoever reads it.
  3. Verify every fact against the source, and say what you couldn't verify.
  4. For voice, a profile and real examples before fine-tuning, and watch what the model adds.
  5. Code isn't given to the model to rewrite: it's protected and restored.
  6. Secret redaction: automatic and blocking.
