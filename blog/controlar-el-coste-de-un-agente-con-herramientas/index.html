12 million tokens in one afternoon: how to control the cost of a tool-using agent

A Neon session burned through 12 million uncached tokens, and a unit error turned it into a $2,400 scare. What really happened, and the four safeguards that work for any tool-using agent.

Neon · costBack to blog

On September 19 I had a long conversation with Neon, my voice assistant, going over the state of Saturno. Nothing unusual: I asked how the tasks were going and he ran commands to find out. A few days later, Anthropic's cost report said that session had cost about $2,435. This chapter covers what actually happened, and it's two very different things: a real technical failure that needs to be understood, and a measurement error that turned about $24 into a two-thousand-dollar scare. Above all, it covers the protections I built afterwards, because they apply to any agent with tools.

What actually happened

The first thing was to rule out the worst case: had someone gotten in through the tunnel? In the incident window there were four WebRTC connections, one after another and not simultaneous, all from my IP and through the same TURN relay I have configured. The transcribed conversation was mine. There was nobody else.

The second thing was the volume. I cross-checked the logs against Anthropic's usage report (which gives tokens, not money) and got this:

  • 256 API calls across the whole window, with no errors or hidden retries.
  • About 12 million input tokens, about 8.86 million of them in the peak hour alone.
  • About 47,000 tokens per call on average. It wasn't thousands of tiny calls: it was a few calls, each with an enormous context.
  • Cache at zero. cache_creation and cache_read were both zero for the whole peak hour.

Once you see it, the mechanism is obvious. Neon ran shell commands to query Saturno (journalctl dumps, SQLite queries) and every output went into the context in full. Every reconnection reloaded the accumulated history. And with no cache, each of those 256 calls paid again from scratch for the system prompt, the entire history and all the command outputs accumulated up to that point. With tools enabled, the context grows on every turn, and the cost of each call grows with it: total spend doesn't rise linearly with the conversation, it rises much faster.

The measurement error: $2,435 that was really $24

For days I worked with the $2,435 figure. Then one day I put $10 into the account, which was at −$0.69, and the next day I had $7.76 left. Actual consumption had been $1.55. The API cost report said 156.09 for that same day.

156.09 divided by 100 is 1.56. The amount field in the Cost Report isn't in dollars but in cents, and we were reading it as dollars without a second thought. Applied to the day of the incident, the $2,435 was about $24, which also fit with the account having ended at −$0.69 rather than owing thousands.

What was still valid is the important part. The whole technical diagnosis had been done with token counts from the usage report, not with amounts, so the 12 million tokens and the zero cache were real. What was wrong was the translation into money.

Lesson: before reacting to a cost figure, cross-check it against something that doesn't come from the same source; in my case, the actual balance of the account. And measure agents in tokens, which is the unit you actually control. Dollars are a conversion, and conversions break.

The fact that it was $24 and not $2,400 doesn't change the conclusion. The same mechanism, with a longer conversation or a more expensive model, scales without a ceiling. Since the incident I've been clear on this: making sure it can't blow up again matters more than the bot always being available.

Protection 1: a prompt cache that actually works

The first step was to turn on prompt caching, which in Pipecat is done with an option on the Anthropic service. But that option only marks user messages for caching, not the system prompt, which is long. So the system prompt is cached separately, with a one-hour cache: in a voice conversation there are long pauses that would make the default 5-minute cache expire.

The numbers speak for themselves: a normal session, with lots of tools and with the changes already in place, on September 23 had about 24 uncached input tokens and about 477,000 served from cache.

Protection 2: prune the context by asking "is it still enough?"

The cache makes repeating the context cheaper, but it doesn't stop it from growing. For that I needed to remove what's no longer useful, above all old command outputs. The first idea was to ask a model, item by item, "is this still relevant?". The problem is that working memory doesn't work like that: two things that look dispensable on their own can be needed together.

So I flipped it around and redesigned it as a single question, asked globally: "if I remove this, is the context still enough for what's being asked right now?". It's tested on each old tool output, from oldest to newest. If it's still enough, it stays out; if not, it's restored. It's literally delta debugging (Zeller's ddmin algorithm, which is used to minimize test cases), but applied to an LLM's context.

for i in new_candidates[:max_attempts]:
    original = messages[i]["content"]
    messages[i]["content"] = PRUNE_PLACEHOLDER_PREFIX       # lo quito para probar
    sufficient = await is_context_sufficient(last_user_text, _render_for_jev(messages))
    if sufficient is None:                                  # el juez no responde:
        messages[i]["content"] = original                   # restauro y no adivino
        break
    decisions[i] = bool(sufficient)
    if sufficient:
        archive_id = archive_pruned(username, original)     # se archiva, no se pierde
        messages[i]["content"] = _prune_placeholder(archive_id)
    else:
        messages[i]["content"] = original

The judge is Jev, a small and very cheap model that I reach through OpenRouter. Several details came out of real problems:

  • The 4 most recent messages are never touched, and outputs shorter than 200 characters aren't evaluated: the call isn't worth it.
  • Decisions are memoized per session. Without that, since the protected window keeps shifting, the same candidates were asked about again on every turn, which added about 3.6 seconds of sequential calls to Jev per turn to get almost always the same answer.
  • Pruned content isn't lost. The original content is archived and a marker with an archive_id is left in its place. If it turns out to be needed later, Neon has a tool to retrieve it. Something not being needed for this request doesn't mean it will never be needed.
  • If Jev doesn't respond, everything is kept. When in doubt, better more context than less.

The bug that nullified pruning without raising any errors

For a while the pruning almost never removed anything, and nothing was failing, which is what made it strange. Jev's client trimmed the context to 8,000 characters, keeping the end. But a 40-message conversation already took up more than 11,000 characters, and the end is exactly where the candidates aren't, because the candidates are the oldest content. Jev was judging whether the context was enough without an item on a view that didn't even contain it. I fixed it by raising the limit to 60,000 characters and, if trimming is needed, keeping the beginning and the end, never just the end.

Pruning and caching fight each other if you're not careful

The first design built a pruned copy of the context on every turn to send. It reduced tokens, but it broke the cache: Anthropic's cache needs the prefix to be identical byte for byte, and a different copy on each call forced it to be rewritten. Measured the same day, one pruned call read 4,399 tokens from cache and wrote 28,452 new ones.

The solution was to collapse the messages permanently, in the context itself, the first time it's confirmed they're not needed. That way each message changes only once, and from then on all calls reuse exactly the same content, so the cache is read cheaply instead of being rewritten. Only a new candidate causes an occasional rewrite.

Lesson: any optimization that changes the prompt's content between calls competes with the cache. Make changes once and make them final, not on every call.

Protection 3: brakes that fail closed

The cache and pruning reduce the normal cost, but they don't protect against a loop. For that there are three independent brakes in the LLM service subclass, and all of them fail toward "cut the session", never toward "keep going, even if it's worse":

  1. Per-session token budget. An estimate (characters divided by 4) accumulated per session, with a ceiling of about 750,000 tokens, which depending on the model is a few dollars. If it's exceeded, the session ends. It doesn't skip calls or hang: it ends.
  2. Rate limiter. More than 15 LLM calls in 60 seconds cuts the session immediately, regardless of how big each call is. It's the exact signature of the incident (bursts of several calls within a few seconds, sustained for more than an hour), and a token budget takes a while to detect a loop of many small calls.
  3. Degraded mode. If Jev stops responding, pruning is no longer possible and the context will grow faster per call. The safe move is to lower the ceiling to 150,000 tokens for the rest of the session, not to keep going without pruning at the normal ceiling.
async def _process_context(self, context):
    if self._rate_limited():
        await self._stop_session("más de 15 llamadas en 60 s: patrón del 19/09")
        return
    pruned, jev_ok = await _minimize_context(context, ...)
    if jev_ok is False:
        self._jev_unavailable = True            # techo estricto el resto de la sesión
    budget = SESSION_TOKEN_BUDGET_DEGRADED if self._jev_unavailable else SESSION_TOKEN_BUDGET
    self._session_token_estimate += len(json.dumps(pruned.messages)) // 4
    if self._session_token_estimate > budget:
        await self._stop_session("presupuesto de tokens superado")
        return
    return await super()._process_context(pruned)

So that the ceiling isn't a cliff (everything normal up to the limit and then the session suddenly dies), from 70% of the budget onwards pruning becomes more aggressive: candidates as short as 80 characters and twice as many attempts. The context gets lighter before it hits the wall.

Protection 4: audit every session against real data

The incident went unnoticed until I looked at the balance. Anthropic's admin API doesn't alert on anything, so when each session disconnects, a background task queries the usage report for that time window and, if uncached input tokens exceed 100,000, notifies me through the same Telegram bot that Saturno uses. It looks at tokens, not amounts, because of the earlier lesson. And it has its own safety contract: any failure (missing key, network error, odd response) is logged and ignored, because it must never affect the bot's shutdown.

What I take away from this

  1. In an agent with tools, the context is the cost. Every tool output that goes in is paid for on all the following calls.
  2. Cache first, and make sure it covers what you think it covers (the system prompt wasn't included).
  3. Prune with a global question, not item by item, and archive instead of deleting.
  4. Optimizations that change the prompt compete with the cache: one-time, final changes.
  5. Brakes that fail closed: budget, rate and a degraded mode that's stricter, not more permissive.
  6. Measure in tokens and cross-check money figures against an independent source before getting alarmed.
  7. Audit every session automatically. Spending you only discover by looking at the balance always arrives late.
