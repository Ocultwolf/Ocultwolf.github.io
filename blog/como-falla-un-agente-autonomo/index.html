How an autonomous agent fails: six real Saturno breakdowns

Getting an agent to work on its own is easy; the hard part is getting it to fail well. Six real Saturno breakdowns, their causes, their fixes, and the pattern behind each one.

Autonomous agentsBack to blog

Saturno is the system I have working on its own across my projects while I'm not at the keyboard. The idea is simple: if the task queue empties, I don't want it to sit idle waiting for me to tell it something. I want it to find the next useful step and do it. What I've learned is that getting an agent to work on its own is easy. The hard part is getting it to fail well. Here are the six real breakdowns I had in September, what caused them, how I fixed them, and the pattern behind each one.

How it's built

Saturno is a Python daemon managed by systemd, independent of any open session. Internally it's a LangGraph graph with separate nodes, and a different backend plays each role:

cola de tareas (SQLite) ──► triage ──► Codex escribe el código (vía proxy fcc-server)
                                            │
                                            ▼
                                   Claude revisa el diff
                                   ├─ aprobado ──► queda en el working tree para revisión humana
                                   └─ rechazado ──► Codex reintenta con el feedback
                                                     └─ 2 rechazos seguidos ──► Claude lo arregla directamente

cola vacía ──► planificador de objetivos (Claude, solo lectura) ──► propone el siguiente paso

Three design decisions matter for what comes next:

  • One writes, another reviews. Codex writes the code and Claude reviews it. If the reviewer rejects twice in a row, there's no point in pushing the same feedback at the weaker model again: Claude edits directly.
  • Long-term goals. When there are no tasks, a planner reads the real state of the project (git log, git status, documentation) and proposes a small, verifiable step. It re-plans each goal at most every 30 minutes, and what it proposes goes in with lower priority than what I ask for myself.
  • It never commits. Everything stays in the working tree. Closing a change into the repository history is always my decision.

With this running, the breakdowns began.

Breakdown 1: the dead proxy that looked like a bug

Every call to Codex goes through a proxy, fcc-server, which nothing was supervising. When it went down, every dispatched task failed in under a minute with a "blocked" that said nothing. The problem is that, from the outside, that is identical to a real bug in the task: the reviewer saw failures, the attempt counter went up, and the goal ended up flagged as problematic because of what was simply a dead process. I had to bring it back up by hand more than four times in a single session.

I fixed it by making the Codex client check the proxy's health before every call (an HTTP request from inside the container) and restart it if it doesn't respond. I verified it the only way I trust: I killed fcc-server by hand and checked that the health check detected it and brought it back up.

Pattern: an autonomous agent has to distinguish between "the task failed" and "the infrastructure failed". If both add to the same failure counter, the system punishes the work for the environment's fault.

Breakdown 2: the poisoned environment

Six cycles in a row, over three hours, used up all their retries without ever reaching a real review. Codex runs as root inside a container, with the project folder mounted from the host. When it ran uv sync, the resulting .venv ended up owned by root on the host, and from then on neither the reviewer, nor Codex's next attempt, nor I by hand could run the tests, the linter or the type checker. Codex was literally unable to verify its own work. As soon as I repaired the environment by hand, the whole suite passed: 268 tests green, ruff and mypy clean. The code change had been fine from the start.

The first fix was to hand ownership of the folder back to the host user after every run. It wasn't enough. uv writes the link to the venv's Python interpreter as an absolute path under the $HOME of whoever creates it, and inside the container that $HOME is /root. So the same string points to two different directories depending on who resolves it: inside the container it's the Python that uv just installed, and from the host it's the real root's home, with 700 permissions. It doesn't matter who owns the link: from the host it always gives permission denied.

The final solution was to delete the venv after every Codex run, from inside the container, instead of trying to repair it. The next step recreates it in its own context, which is the right one.

# después de cada ejecución de Codex, gane o pierda: se borra desde dentro del contenedor...
subprocess.run(["docker", "exec", container, "sh", "-c", f"rm -rf {project}/.venv"], check=False, timeout=30)
# ...y el chown -R sigue corriendo para el resto de lo que Codex deja como root (logs, __pycache__...)

Pattern: every step an agent takes has to leave the environment as it found it. If one step dirties the ground, every later step fails over something that has nothing to do with what it's doing, and retries only multiply the problem.

Breakdown 3: the standing invitation

This is the one that taught me the most. I left the daemon working alone overnight and, for about 19 hours, every cycle of roughly 30 minutes failed in exactly the same way. Each failure reached me on Telegram, all night, and nothing stopped it.

The cause wasn't in the code, it was in a document. The planner had found a legitimate problem (a concurrency test that depended on fcc-server being alive) and tried to make it hermetic. The attempt didn't work and was reverted. But the project's evidence document listed it as "pending", and the planner, which reads the documentation to decide the next step, interpreted that on every cycle as an invitation to try again. It proposed the same impossible fix, it failed, it was reverted, and around we went.

The fix had two parts:

  1. A failure budget per goal, not just per task. Each goal carries a counter of consecutive failures among the tasks it generates. A success resets it to zero; on the third failure in a row, the goal moves to paused and a single notice goes out explaining why, instead of one notice per attempt.
failures = int(row["consecutive_self_start_failures"]) + 1
should_pause = failures >= max_consecutive_failures  # 3
con.execute(
    "UPDATE objectives SET consecutive_self_start_failures = ?, "
    "status = CASE WHEN ? THEN 'paused' ELSE status END, updated_at = ? WHERE id = ?",
    (failures, should_pause, _utc_now(), objective_id),
)

Every way a task can end (approved, retries exhausted, wall-clock timeout, wrong branch or unhandled exception) goes through the same function, which records the result against its goal. The planner's own failures count too, so that a broken planner call can't spin in a loop without anyone finding out.

  1. Rewriting the document so it stopped reading like an open task.

Pattern: for an agent, everything it reads is prompt. Project documentation, TODOs and evidence documents are not neutral context: they are instructions. A per-task retry limit isn't enough, because the planner can create an identical new task every time. The budget has to live at the level that generates the work.

Breakdown 4: the agent that wanted to commit

While investigating breakdown 2 I found something worse: the planner had queued a task asking Codex to commit a document on its own. Saturno closing changes without supervision should not have been possible, but the planner's prompt simply didn't forbid it. I added it explicitly: never instruct the programmer to commit, push, merge or tag; the result stays in the working tree for me to review.

Pattern: irreversible actions, or ones that reach outside the system, get forbidden explicitly and at every level, starting with the one that decides what to do, not just the one that executes. The fact that something "has never been asked for" doesn't mean the agent won't propose it.

Breakdown 5: the pause that wasn't a failure

With automatic pausing working, the opposite problem appeared. The most frequent cause of three failures in a row wasn't a bug, but my Claude account's session limit. September 19 shows up very clearly in the logs: from a certain point on, every new session lasted a moment and ended with "You've hit your session limit · resets 1:30pm". That repeated roughly every 20 minutes until the reset time, and the first attempt after it worked normally.

Pausing the goal in that case is right, but leaving it paused forever is not. For that I wrote a watchdog that checks Saturno's state every three minutes:

  • If a goal is paused because of the session limit, it reads the reset time from the error message itself and reactivates the goal only once that time has passed, without notifying anyone.
  • If a task exhausted its retries and needs a person, another agent reviews it first, and only if that one doesn't resolve it either does it notify me on Telegram.
  • If the daemon's service or the Telegram bot's service isn't active, it restarts them.

There was a small lesson here too. The first version, when it couldn't read the reset time, reactivated the goal anyway. That is exactly what you shouldn't do: if the pause came from a breakdown like number 3, reactivating blindly reopens the all-night loop.

Pattern: not all failures are equal. There are at least three classes (infrastructure, quota limits and real task failure) and each calls for a different response: repair, wait or escalate to a person. Automatic pausing and automatic reactivation have to agree on which class of failure they're looking at.

Breakdown 6: the test that barely passed

The last one is more subtle. A stress test fired 20 concurrent requests at the runner and some exceeded the timeout. It looked like a deadlock and I investigated it as one, but the instrumentation showed there was no blocking in either Postgres or SQLAlchemy's connection pool. The bottleneck was the external proxy: it couldn't serve 20 SSE streams at once within its own 30-second limit, so the requests were being serialized behind it.

The task I queued was to raise the client timeout so the test could tell "it hung and never comes back" apart from "it's slower because it's queued", without relaxing any other assertion and requiring two green runs in a row. The first run passed in 249 seconds with a timeout of 250. That isn't a test that passes, it's a test that hasn't failed yet. I adjusted it again with some margin, and the next two runs passed in 274 and 377 seconds.

Pattern: a timeout is not proof of correctness, it's an assumption about the infrastructure. When a test depends on a shared external service, you have to measure before deciding whether the problem is concurrency or capacity, and distrust any green that arrives with just enough margin.

What I take from this

If I had to build Saturno again from scratch, I'd start with this before any feature:

  1. Classify failures into infrastructure, quota and task, and never add them to the same counter.
  2. A failure budget at the level that generates the work (the goal), not just the task.
  3. Environment hygiene: every step leaves the ground as it found it, and if it can't repair it, it deletes it.
  4. Treat documentation as prompt: what the agent reads decides what it will do.
  5. Forbid the irreversible explicitly and at the level that plans.
  6. One notice with an explanation instead of a hundred notices with no context.
  7. Verify by breaking it: kill the process by hand, force the error and see what the system does.

None of these failures was hard to fix once I understood it. What was expensive was that, while they were unfixed, the system kept working, spending time and calls, and warning me about problems that weren't the real ones. An autonomous agent that fails silently, or that fails in a loop, is worse than having no agent.
