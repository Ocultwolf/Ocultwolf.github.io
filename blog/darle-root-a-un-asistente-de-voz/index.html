Giving a voice assistant root (and why I ended up taking it away)

The layers I added to make a voice assistant with root access reasonable, what each one protects and what it doesn't, and why the safest decision was to take the shell away from the model that does the talking.

Neon · securityBack to blog

I wanted an assistant I could tell "find out why that service went down" or "restart this" and have it do it, on my machine, with real permissions. That means giving a language model that listens through a microphone and is exposed to the internet through a tunnel the ability to run commands as root. In this chapter I walk through the layers I added to make that reasonable, what each one protects and what it doesn't, and why in the end the safest move was to take the hands away from the one doing the talking.

Layer 1: nobody gets in without an account

Neon is used from the browser through a Cloudflare tunnel. Without authentication, anyone who found the URL could connect and talk to an assistant able to run commands on my machine. So the first thing was to close the front door: the endpoint that starts a session returns 401 if it doesn't receive a valid token.

The design:

  • Passwords with bcrypt, never in plain text. If the user doesn't exist, a bcrypt check is still run against an arbitrary value, so the response time doesn't reveal which users exist.
  • Opaque session tokens kept on the server, not signed JWTs: ending a session or making it expire is just deleting an entry from a dictionary, with no key rotation. They last 30 days and are lost if the process restarts, which for a personal tool seems acceptable to me.
  • Lockout after failed attempts: 5 failures from the same origin block login for 15 minutes.
def verify_credentials(username: str, password: str) -> tuple[bool, str | None]:
    user = _load_users().get(username)
    if user is None:
        # bcrypt se ejecuta igualmente: un usuario inexistente no se distingue por tiempo
        bcrypt.checkpw(password.encode("utf-8"), bcrypt.gensalt())
        return False, "no_such_user"
    if not bcrypt.checkpw(password.encode("utf-8"), user["password_hash"].encode("utf-8")):
        return False, "bad_password"
    if user["status"] != "approved":
        return False, "pending"
    return True, None

The specific reason is only used internally: outwardly, the login always responds with a generic message.

Layer 2: signing up is not getting in

I wanted to be able to invite other people without having to create their accounts myself, so registration is open, but a new account starts out as "pending" and can't log in until someone approves it. The first account created is the owner's and is approved automatically, because somebody has to be able to approve everyone else.

What matters is where the approval happens: there is no web interface for it, on purpose. Approval is done out of band, with a script on the machine. That way, a pending account can't approve itself, no matter what it does from the browser.

Lesson: the action that grants privileges shouldn't be available through the same channel used by the person asking for them.

Layer 3: everyone's memory is their own

Once there were several users, a less obvious risk showed up. Neon keeps the conversation history so it can continue across reconnections, and that history contains everything, including the trust that has been built up for running commands as root. If all users shared the same file, a guest would inherit the owner's context. That's why the history is stored per user.

And here comes the bug I described in the chapter on Neon: the username never reached the bot (it was in the wrong place in the request), so for days every session landed in a generic shared history. It threw no error. Per-user separation was "implemented", but it didn't work.

Lesson: an isolation measure you haven't tested end to end isn't an isolation measure. You have to verify that the data that separates users actually arrives where it's used.

Layer 4: confirm out loud before anything irreversible

Neon's shell tool had a confirmed parameter. If a command looked destructive, the tool didn't run it: it returned needs_confirmation with the instruction to repeat it to me out loud and wait for an explicit yes. Only then could the model call it again with confirmed=true.

So as not to depend only on the model's judgment, I added a list of patterns that forces that confirmation for anything that clearly looks irreversible: rm -rf, dd, mkfs, shutting down or rebooting, stopping services, git push --force, git reset --hard, dropping tables, curl ... | sh, a fork bomb...

if _DESTRUCTIVE_RE.search(command) and not confirmed:
    await params.result_callback({
        "status": "needs_confirmation",
        "command": command,
        "instructions": "Repite el comando en voz alta y pide un sí explícito. "
                        "Solo vuelve a llamar con confirmed=true si confirma claramente.",
    })
    return

Everything is logged: every call to the tool in its own log, and every command run as root in a separate, independent log, with its exit code.

What these layers don't protect

Here I have to be honest, because it's easy to confuse layers that look like security with layers that actually are:

  • The pattern list is a heuristic. It catches the obvious, but a destructive command written a different way won't trigger it. It's defense in depth, not a barrier.
  • The model handles the confirmation. The confirmed parameter is set by the LLM itself. The instruction is clear, but it's still an instruction to a model, not a control the model can't get around.
  • The root wrapper logs, but doesn't restrict. Sudoers only allows one specific script, and that script runs whatever command it receives as root. That gives me a clean record of everything executed as root, but in practice it's full root. To really restrict it, I'd need a closed list of allowed operations.
  • It doesn't recognize my voice. I asked for Neon to respond only to the voice of whoever had logged in. What got built was the login; voice recognition was left pending. Anyone who speaks near my microphone during an open session is talking to Neon.

Lesson: before calling a layer "security", ask yourself what happens if the model gets it wrong or if someone writes the same command a different way. If the answer is "it runs anyway", it's a log or an aid, not a control.

The decision that added the most security: taking away the shell

Everything above was an attempt to make it reasonable for a conversational model to have root. When I separated the conversation from the work (the previous chapter on Neon), the conclusion was simpler: the model that talks doesn't need to touch the system. I took the shell tool away from it. Now Neon can only delegate: the work is done by a background agent, which is the only real path to the machine.

The risk doesn't disappear, it moves. The background agent works with nobody listening, so spoken confirmation no longer exists: its rules (don't make up results, nothing irreversible without permission) live in its prompt. But the surface shrinks a lot. The model exposed to whatever is said into the microphone can no longer execute anything, and the one that executes only receives written, logged tasks.

Lesson: the most effective way to secure a dangerous capability is usually not to give it to the most exposed component. Reducing who can do something is worth more than adding layers around whoever shouldn't be doing it.

What I take away

  1. Close the entry point first: an assistant with tools exposed without authentication is a public shell.
  2. Actions that grant privileges, out of band.
  3. Verify isolation end to end; it's not enough for it to be implemented.
  4. Tell controls from aids: heuristics, instructions to the model and wrappers that only log are not barriers.
  5. Log everything that runs with privileges, even if you can't restrict it.
  6. Take dangerous capabilities away from the most exposed component.
