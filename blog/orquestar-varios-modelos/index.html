Orchestrating multiple models: each in its place

Half a dozen models, each in its own role: the expensive one where judgment matters and the cheap one where its mistakes get caught. The patterns that work, and what happens when the one that fails is the reviewer.

Agents · modelsBack to blog

No quiero depender de un solo modelo. Not on principle, but out of pure arithmetic: some jobs need the best model available, others a small model does just as well for a fraction of the price, and others come out free if you send them down the right path. Right now my systems have half a dozen different models, each with its own role. In this chapter I explain how I've split them up, which patterns have worked for me, and what happens when the one that fails is the strong model, the one that reviews all the others.

The map

Role Model Why that one
Voice conversation (Neon) Claude Haiku Cheap and fast; it only talks, it doesn't do work
Context judge ("is it still enough?") Jev, via OpenRouter Cents per million tokens, free output, 4 s timeout
Saturno's programmer Codex with an NVIDIA NIM model, through a proxy Almost no cost; weaker, which is why it gets reviewed
Saturno's reviewer and fixer Claude (Claude Code) The most reliable judgment in the system
Goal planner Claude, read-only Reads the project's real state and proposes the next step
Neon's background agent claude -p on my subscription Heavy work without paying for the API
Blog generation and voice Claude Sonnet Good writing at a moderate cost

The underlying rule is simple: the expensive model only where judgment matters, and the cheap one where a mistake can be caught and corrected.

Pattern 1: a cheap one writes, a strong one reviews

In Saturno, the code is written by Codex with a model served by NVIDIA NIM through a proxy, practically for free, and reviewed by Claude. If the reviewer rejects twice in a row for the same reason, there's no point in sending the same feedback to the weak model again. What I do is escalate to a fixer, which is Claude with write permissions, and it applies the fix itself, because it already diagnosed the problem while reviewing.

def _route_after_supervise(state: SaturnoState) -> str:
    stuck = (
        state.get("supervisor_verdict") == "rejected"
        and state.get("consecutive_rejections", 0) >= settings.auto_fix_threshold   # 2
        and not state.get("auto_fix_used")
    )
    return "auto_fix" if stuck else "reflect"

In practice, the reviewer's rejections were very specific and almost always the same kind: code that didn't compile because of broken indentation, a badly indented test fixture, an absolute path put in by hand, a try/except that was added and left the file unable to compile. The cheap model makes mistakes that a reviewer catches in seconds, and that's exactly what makes the split pay off.

Lesson: a cheap model with a strong one reviewing comes out better than the strong one doing everything, as long as the cheap model's mistakes can be detected. And if the same mistake repeats twice, switch models instead of repeating the feedback.

Pattern 2: when the reviewer is the one that fails

Saturno's numbers from September 2 to 23 in JARVIS-PD told me something I didn't expect. Out of 104 tasks:

  • 51 were approved by the reviewer.
  • 38 used up their 5 attempts without approval, and I ended up approving them by hand.
  • 6 were resolved by the fixer.
  • 3 were approved by Neon and 5 ended in error.

What caught my attention is in those 38. In 28 of them the reviewer left no usable feedback: either the field was empty, or what was there was the raw response of a call that never actually did anything, with zero milliseconds of API time and zero cost. In other words, in most cases the one failing wasn't the programmer but the reviewer; most likely because of session limits, timeouts, or calls that never even ran. And from the outside that looks the same as "the programmer can't get approved": the attempt counter goes up and the task runs out.

Lesson: in a "one writes, another reviews" chain, the reviewer is a single point of failure. A verdict that never arrives can't count as a rejection: you have to tell "rejected with a reason" apart from "no review happened", just as in the chapter on outages I had to tell task failures apart from infrastructure failures.

Pattern 3: route for independence too

Saturno's triage is deliberately dumb: it looks for keywords in the goal. If it sounds like code, it goes to the programmer; if it sounds like design or research, to the planner; otherwise, to Claude in conversation mode. And if the programmer's call budget runs out, it falls back to a local model.

if any(hint in goal for hint in CODE_HINTS):
    next_agent = "codex-worker"
elif any(hint in goal for hint in DEEP_HINTS):
    next_agent = "codex-planner"
else:
    next_agent = "claude-chat"

The most interesting part is the last branch. In principle, anything that isn't code should go to a local model (Ollama, through the OpenClaw gateway). But that route had a bug of its own in OpenClaw when compacting transcripts, independent of the model. As the fallback I chose Claude directly, and not for its quality: it uses a different authentication and quota from Codex's, so it can never compete with the programmer for the same session or go down because of the same limit.

Lesson: when choosing the fallback model, also check whether it fails independently. A fallback that shares a quota or authentication with the primary goes down at the same time as the primary.

Pattern 4: the same model by another path is a different product

Two examples of this:

  • The gateway that pointed to an expired session. OpenClaw's routing for the programmer was still pointing to an expired ChatGPT OAuth session, and its way of switching providers wasn't being applied reliably. The fix was to bypass the gateway and launch Codex directly inside the container against the NVIDIA NIM proxy, which was already tested.
  • Kimi Code versus the Moonshot API. When I tried Kimi as the programmer, the task died on a limit of 3 requests per minute. Looking into it, it turned out there are two different endpoints: the Kimi Code product's, with its own authentication and a very low limit, and Moonshot's general API, with its own key. Same model, two products with completely different limits. One caveat, though: the fact that an isolated API call worked didn't prove there wasn't also an account-level limit, because a single call never triggers a "maximum 3 per minute".

Lesson: when you evaluate a model, evaluate the whole path: gateway, authentication, limits and permission mode. Half of the problems I had with new models weren't the model's fault.

Pattern 5: small models as judges, with a safe default

Jev is the clearest example. To decide whether an old tool output can be removed from Neon's context, you don't need a big model: a yes-or-no question is enough ("is the context still enough without this?"), and a small model answers it for cents. The key is what happens when it fails. If Jev doesn't respond or responds with something unusable, the answer is treated as "don't remove it": when in doubt, more context, never less. And if it fails once in a session, I stop calling it and switch to a stricter budget.

Lesson: a small model can act as a judge in bounded decisions, as long as its failure has a safe default and doesn't block the rest of the system.

Pattern 6: evaluate a new model without trusting it

When I put Kimi to work on a separate branch, the rule was not to trust what it said it had done: the evaluation had to be independent, with tests, reviewing the diff and checking whether it met what was asked. In the end nothing could be evaluated, because it died on the request limit before touching any code. But from the little it did, the reasoning was good: it understood the project's state and the goal well. That "couldn't be evaluated" is also a result, and I wrote it down as such instead of drawing conclusions from an experiment that didn't finish.

What I take away

  1. The expensive model only where judgment matters; the cheap one, where its mistakes can be detected.
  2. Escalate to a stronger model after two identical rejections; don't repeat the same feedback.
  3. The reviewer fails too: tell "rejected" apart from "no review happened".
  4. Choose fallbacks that fail independently (a different quota, a different authentication).
  5. Evaluate the whole path, not just the model: gateway, limits, permissions.
  6. Small judges with safe defaults.
  7. Evaluate new models independently, and an experiment that didn't finish is not a negative result.
