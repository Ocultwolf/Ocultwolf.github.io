A voice assistant's memory: what to remember, where, and how to admit you've forgotten

An assistant's memory isn't one thing: it's five layers with different lifetimes, costs and failure modes. Every "it lost its memory" bug I diagnosed came from a different layer.

Neon · memoryBack to blog

“Neon ha perdido memoria” (“Neon has lost its memory”) was one of the complaints I repeated most while building it. Every time I sat down to investigate, the cause was different. An assistant's memory isn't one thing: it's several layers, with different lifetimes, costs and ways of failing. In this chapter I go through them one by one, with the specific failure that taught me each one.

Layer 1: the conversation that survives reconnections

By default, every Neon connection started with an empty context, so every reconnection was like talking to a stranger who introduces themselves all over again. I wanted a single continuous conversation, even if I switched it off and on. The solution is simple: on disconnect the history is saved to disk, per user, and on connect it's loaded. If there is already a history, Neon doesn't greet me; it waits for me to speak.

MAX_MESSAGES = 300

def save_history(messages: list[dict], username: str | None = None) -> None:
    path = _history_path(username)
    trimmed = messages[-MAX_MESSAGES:]
    path.write_text(json.dumps(trimmed, ensure_ascii=False, indent=2), encoding="utf-8")

The history has a limit so it doesn't grow forever, and that's where the first failure showed up. At first the limit was 80 messages, and Neon "lost its memory" within a single afternoon of work. It's not that it had no access to anything. Every time it ran a command it used at least two messages (the call and its result), so the 80 ran out very fast and the real conversation got trimmed. I raised it to 300.

The username that decides which file gets loaded goes through a strict regular expression before it becomes a path. It's the same pattern that's validated at registration, so a tampered username can't be used to write outside the directory.

Lesson: in an agent with tools, a memory limit measured in messages doesn't measure the conversation. Tools eat the window long before words do.

Layer 2: knowing how to say "I don't have that anymore"

That same day I found something more important than the limit. When I asked about something that had already been trimmed, Neon would tell me it had no access, or it would simply act as if it had never existed. Both answers are worse than the truth. Now it knows where its memory lives and what to say when something old is gone: that it was lost because of the history limit, without inventing that it never existed.

Lesson: an assistant with finite memory has to know its own limits and say so. "I forgot it because I have a cap" builds trust; "I don't have access" or an invention destroys it.

Layer 3: what gets pruned is archived, not deleted

In the chapter on cost I described how Neon prunes tool outputs from the context once they're no longer needed. That pruning is permanent, to avoid breaking the cache, but the fact that something isn't needed for the current request doesn't mean it will never be needed. So, before replacing a result with a marker, the original content is saved to an append-only file, per user, and the marker carries its identifier:

[resultado de comando anterior omitido para ahorrar contexto -- ... Si más adelante hace falta
de verdad, se puede recuperar con la tool recall_pruned_context, archive_id="..."]

Retrieving it is a lookup by identifier, without going back to the model that decided to prune it. The file is append-only because entries are never edited, only queried. And it respects the same per-user separation as the history: another user's identifier simply isn't found.

Lesson: when you shrink the context to save money, always leave a way back. The marker has to say what's missing and how to get it back, not just that something is missing.

Layer 4: working memory lives somewhere else

A good part of "what Neon knows" about my projects isn't in Neon, but in my Claude Code sessions, each with its own working context. That's why Neon has tools to list those sessions, read their history and send them instructions, all through the HTTP bridge I described in the chapter on separating the conversation from the work. Instead of copying each project's memory into Neon, it queries it where it already lives.

This also has its own way of failing. One day I wanted to recover a session I had renamed "blog" and had given up for lost. I searched the project folder and found about 90 sessions, all automated runs of the post generator, none longer than 35 lines. The name of a tmux session doesn't have to match the folder where the Claude conversation inside it lives, so searching by folder didn't find it. You have to search by content.

Lesson: querying memory where it already lives is better than duplicating it, but you need a reliable index of where each thing is. The names we humans pick (for sessions, for windows) are not that index.

Layer 5: knowledge that isn't conversation

The last layer is my notes: an Obsidian vault with guides, references and scribbles. I wanted my bots to be able to browse it, not just me from the app. Neon has read-only access (list notes, search by keyword and read a note) through the same bridge, because the vault lives on the host and Neon runs in a container.

I made two deliberate decisions. The first, read-only: if something needs to be saved to the vault, a Claude Code session does it with its own skill, not the voice assistant. The second, keyword search, not vector search: right now the vault has a handful of notes, and setting up embeddings for that would be solving a problem I don't have yet. When there's enough content for keyword search to fall short, that will be the time.

Lesson: don't build a retrieval system more complex than the volume of knowledge you have. Start simple and write down when it stops being enough.

A separate case: the instruction that wasn't applied

I asked Neon to answer briefly from then on, with no explanations unless I asked for them, and to always remember it. No way. When I looked into it, I saw that Neon had in fact edited its own prompt to save it, twice, and the two edits partly overwrote each other. But the running process still had the old prompt loaded in memory: the change would only apply on restart, and Neon couldn't restart itself without cutting off my call. I reduced it to a single clean instruction and restarted the service.

Lesson: an agent being able to modify its own configuration doesn't mean the change is active. Distinguish between what's saved on disk and what the process has loaded, and tell the agent which of the two has changed.

A warning about testing memory

When I split the memory by user, the test consisted of creating a test user and checking that their history didn't get mixed with mine. During that test my real history file was accidentally overwritten. I restored it from a backup before continuing, but the lesson is clear: persistence tests are run on isolated paths, never in the same directory where the real memory lives.

What I'm taking away

  1. Memory is layers, and every "it lost its memory" comes from a different one: diagnose which before touching anything.
  2. Measure limits in content, not in messages, if tools are involved.
  3. Teach the agent to admit it has forgotten, and to say why.
  4. What gets pruned is archived, and the marker explains how to get it back.
  5. Query memory where it already lives, with a reliable index and not with human names.
  6. Retrieval as simple as the volume allows: keywords before vectors.
  7. Saved is not applied: an agent's configuration changes need to know when they take effect.
  8. Memory tests, on isolated paths.
