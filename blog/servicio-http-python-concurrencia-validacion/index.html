A Python HTTP service under pressure: concurrency, validation, and the deadlock that wasn't

A small HTTP runner that enforces token budgets taught me more about robustness than almost anything else: concurrency, layered validation, mocks that miss their target, a deadlock that didn't exist, and approved work that got lost.

JARVIS-PD · robustnessBack to blog

Inside JARVIS-PD, my agent-system project, there's a small but critical piece: an HTTP runner that sits in front of every model call and enforces a token budget before letting it through. It's a few hundred lines, and it still taught me more about robustness than almost any other part of the system. Agents did part of the work (Codex writing, Claude reviewing), so this chapter is also about something less obvious: how people fool themselves with evidence, whether they're human or agent.

What the runner does

It's a policy enforcement point. It receives a request, validates it, counts the input tokens locally, reserves the invocation in PostgreSQL with an idempotency key, calls the provider with streaming (SSE) and, when it finishes, compares actual usage against what it had estimated. If the difference exceeds the policy's tolerance, it persistently blocks that version of the policy until someone reviews it.

POST ──► validar ──► contar tokens ──► reservar en Postgres ──► llamar al proveedor (SSE)
                                         (idempotencia +             │
                                          política no bloqueada)     ▼
                                                           comparar uso real vs estimado
                                                           └─ desvío > tolerancia ──► bloquear política

The reservation locks the policy's state row and that invocation's idempotency row with SELECT ... FOR UPDATE, in that order and inside the same transaction. That way two concurrent requests can't reuse the same key or slip through a policy that has just been blocked.

1. The server that handled one request at a time

The first version used HTTPServer from the standard library, which handles requests one at a time. While one request waited for the provider's response, which can take tens of seconds, all the others queued up. I fixed it by switching to ThreadingHTTPServer, with an orderly shutdown: on SIGTERM or SIGINT it calls shutdown(), which stops accepting new requests and lets the in-flight ones finish.

httpd = ThreadingHTTPServer(server_address, TokenEnforcementHandler)

if threading.current_thread() is threading.main_thread():
    def signal_handler(signum, frame):
        httpd.shutdown()
    signal.signal(signal.SIGTERM, signal_handler)

The test that proves it doesn't check that the two requests "work", but that their time windows overlap. That's the property that really matters: that one doesn't wait for the other.

Lesson: to test concurrency, check the concurrent property (that there is overlap) and not just that each request succeeds on its own. A sequential server passes that second test without any trouble.

2. Validating input in layers

A service that sits in front of something expensive has to reject anything invalid early and cleanly. The cases showed up one by one, several of them caught by Saturno's autonomous planner (and, as I explain in section 6, not all of them are still on the main branch):

  • Non-numeric or negative Content-Length: a 400, not an exception.
  • Body with invalid UTF-8: decoding and JSON parsing were in the same try, which only caught JSONDecodeError. A UnicodeDecodeError slipped through and dropped the connection instead of returning a 400. I fixed it by splitting them into two blocks, each with its own error.
  • Valid JSON that isn't an object (a list, a number): a clean 400, instead of failing later when accessing a field.
  • Usage returned by the provider: input_tokens and output_tokens must be non-negative integers. If the provider returns garbage, it can't be allowed into the accounting.
  • Any other exception around applying the policy: a clean 500 in JSON, never the raw stack trace.
try:
    content_length = int(self.headers.get("Content-Length", 0))
except ValueError:
    return self._bad_request("Invalid Content-Length header")   # resumido: el real escribe la respuesta JSON a mano
if content_length < 0:
    return self._bad_request("Content-Length cannot be negative")

body = self.rfile.read(content_length)
try:
    body_str = body.decode("utf-8")
except UnicodeDecodeError:
    return self._bad_request("Invalid UTF-8 in request body")
try:
    data = json.loads(body_str)
except json.JSONDecodeError:
    return self._bad_request("Invalid JSON")
if not isinstance(data, dict):
    return self._bad_request("Request body must be a JSON object")

Lesson: every decoding step has its own error type. Putting them in a try that only knows one of them is the most common way for a 400 to end up as a dropped connection.

3. The mock that never ran

Two tests used monkeypatch to simulate a malformed SSE response and a generic exception, and they hung until the timeout. The reason is that the runner runs in a real subprocess (subprocess.Popen) and monkeypatch only changes objects inside the test's own process. The subprocess never saw the mock and kept calling the real provider.

The fix was to stop crossing the process boundary with mocks:

  • For the malformed SSE, the test starts a real HTTP server in its own process that serves exactly that sequence of events, and launches a dedicated runner pointing at it.
  • For the generic exception, the runner has an explicit fault-injection point, enabled by a test environment variable, that raises the exception right before applying the policy.

And something else came out of it. With the real code finally exercised, the test's assertion turned out to be wrong: a malformed SSE event is wrapped as a precondition error and the runner returns a 403, not the 400 or 500 the test assumed. That assumption had never been checked, because the mock never actually ran.

Lesson: a mock that doesn't run proves nothing, and neither does the assertion that goes with it. If the code under test lives in another process, simulate at the boundary (a fake server, an environment variable) and not inside it.

4. Evidence from the wrong environment

In one cycle, the agent writing the code delivered a report with 5 failing tests in the targeted tests and 15 in the full suite, with an analysis trying to justify them. The reviewer rejected it. The failures didn't exist: the capture had been made in a different sandbox, against an old copy of the package installed in site-packages instead of the branch's editable code. Run in the right checkout, everything passed.

There was a subtler variant of the same problem. The project's virtual environment didn't have the development tools installed, so pytest was being resolved through the PATH from another project's environment. That time the result was valid by luck, because both environments pointed to the same source code, but I made a note of it.

Lesson: before analyzing a failure, check which code is being tested and with which tools. A test report is worthless if you don't know which package path was imported and which binary ran it.

5. The deadlock that didn't exist

This is the one I like most. A stress test fired 20 concurrent requests at the runner and on every run between 8 and 14 of them ended in a timeout. With PostgreSQL, row locks and concurrency, the obvious hypothesis was a deadlock. So obvious that, on a separate branch, someone went as far as writing a "fix" that reordered the locks before it had been shown that the problem existed.

The real investigation went another way:

  • The deadlock monitor wasn't measuring anything. The script watching PostgreSQL queried deadlock_count in pg_stat_database, a column that doesn't exist (it's called deadlocks). It failed on every run and nobody noticed because nobody read its output. The other check, on pg_stat_activity, only ever saw itself.
  • Instrumenting the pool did give answers. I timed every engine.connect() in two diagnostic runs: the maximum checkout time was 27 ms, the peak was 12 connections out of 15 available, and all pool activity finished within the first 0.34 seconds. Zero mentions of deadlock in all the logs.
  • The bottleneck was outside. Every error was a 30-second read timeout. The proxy standing in for the provider (a single process) couldn't serve 20 SSE streams at once within its own 30-second limit, so the requests queued up behind it. The few that returned 403 did so just after about 31 seconds: it was the upstream timeout turned into a policy error.

The conclusion was written down with its limits: there is no deadlock in either PostgreSQL or the pool; the problem is the capacity of the test upstream. The evidence document also lists what wasn't verified: it was only tested with 20 threads, with the default pool configuration, and always against the proxy, never against the real provider. I adjusted the test to tell apart "it hangs and never comes back" from "it's slow because it's queued", with a more generous client timeout and a configurable upstream one.

Lesson: before fixing a deadlock, prove it exists, and before trusting a monitor, check that it measures something. A broken monitor that makes no noise is worse than having no monitor, because it gives you a peace of mind you haven't earned.

6. Work that isn't committed gets lost

While preparing this chapter I ran into something I didn't expect: the runner's active working branch has almost none of what I describe in sections 2 and 3. The validations, the UTF-8/JSON split, the fault-injection point... all of it exists, but in a WIP commit on a separate branch, saved in a hurry before pausing the work. On the main branch, Content-Length is still converted with an unguarded int().

It's not the first time. In Saturno's task log there's one that literally says "restore the _parse_usage guards and the 8 adversarial tests lost in a git reset". The work was done, approved, lost, and had to be redone.

The cause is a design decision that I defend and that has a cost: Saturno never commits, because closing a change into history is my decision. The result is that approved work sits in the working tree, with no history, and any reset, branch switch or cleanup takes it with it. The rule against autonomous commits is fine. What's missing is the other half: approved work shouldn't sit for days waiting for me to commit it.

Lesson: if your agent can't commit (and it shouldn't), you are the bottleneck. Approved work has to be consolidated early, even if only on a working branch or in a saved patch, or it will end up lost.

What I take away

  1. Test the concurrent property (overlap), not just that each request succeeds.
  2. One error type per step of decoding and validation, and a clean 500 as the final safety net.
  3. Don't cross processes with mocks: simulate at the boundary, with fake servers or explicit injection points.
  4. Check which code and which tools produced a test report before analyzing it.
  5. Prove the bug before fixing it, and verify that your monitors actually measure something.
  6. Write down what you didn't verify. A conclusion with its limits is worth more than one without them.
  7. Consolidate approved work early. Without a commit there's no history, and without history the work gets lost.
