Inside JARVIS-PD: an agent system that has to prove what it does

The core that has to prove what it does: gates backed by reproducible evidence, a Gate 0 that failed, leases with fencing tokens, versioned contracts, six audits for a single worker, and the real cost of so much rigor.

JARVIS-PD · architectureBack to blog

Saturno, the system several chapters of this blog talk about, was born pragmatic: an unstable but working version, built to keep moving. JARVIS-PD is exactly the opposite. It's the core I want to end up replacing everything else, and I'm building it with a rule that sounds bureaucratic and turned out to be the most useful thing in the project: nothing is taken for granted until there's reproducible evidence that it works. In this chapter I cover how it's designed, why a gate that can fail is worth more than ten design documents, and how much all this rigor really costs.

The principles

The project starts from a specification of my own, and a few non-negotiable principles come out of it:

  • PostgreSQL holds the canonical state. Nothing else is a source of truth.
  • Agents propose; deterministic services validate and materialize. A model never writes state directly.
  • LangGraph coordinates, but is never a source of truth. If the graph is lost, it's rebuilt from the database.
  • OpenClaw stays behind ports and adapters, without being coupled to the core.
  • State, outbox and critical audit are committed in the same transaction.
  • Repeatable delivery doesn't mean repeated effect. A message can arrive twice; its effect, never.

The tech is boring on purpose: a modular monolith in Python 3.12, Pydantic for the contracts, SQLAlchemy and Alembic on top of PostgreSQL, and pytest for the evidence. Concurrency invariants are tested against a real PostgreSQL; SQLite can't prove anything.

Phases, gates and evidence

The project moves forward in phases, and each phase ends in a gate with concrete requirements. Gate 0, "Integrity", has ten:

  1. Tasks and executions are only created and change state through authorized paths.
  2. State and outbox are committed in the same transaction.
  3. Repeated messages don't duplicate transitions.
  4. Two workers can't hold the same valid lease at the same time.
  5. A stale fencing token can't write.
  6. Schemas are recreated from scratch with versioned migrations.
  7. Backup and isolated restore recover the expected state.
  8. The audit reconstructs request, authorization and materialization.
  9. The user node contract is versioned, validated and only proposes.
  10. The evidence package makes it possible to reproduce the full evaluation.

Each requirement is proven with executed tests and an evidence package (results, a database dump and hashes) that anyone can reproduce. Project statuses have a strict vocabulary: PASS, READY_FOR_REVIEW, NOT_EVALUATED, SCOPED_NOT_AUTHORIZED. Never "almost ready".

The gate that failed

The first definitive evaluation of Gate 0 came back FAIL, for three reasons:

  • The lease lifecycle was incomplete. The function to acquire a lease existed, but there were no deterministic paths to renew and release it. One test simulated the release by writing directly to the table, and that doesn't meet the contract: if the real system has no such path, the test is testing something else.
  • The controlled release of the outbox had no executed evidence. The inbox one was tested; the outbox one existed in the code, but no test exercised it.
  • A real type error remained. On top of that, the type check wasn't reproducible, because it wasn't pinned in the workflow.

All three were fixed that same day, each in its own commit: reproducible types, a complete auditable lease lifecycle, evidence for the controlled outbox replay, and a hardened restore. After that, Gate 0 passed.

Lesson: a gate that can really fail is the most useful tool in a project. That FAIL found three real gaps that any "by eye" review would have waved through. And a test that simulates a path by writing directly to the database doesn't prove the path exists.

Leases and fencing tokens

Requirement 5 of the gate deserves an explanation, because it's the heart of concurrency. When a worker starts a task, it acquires a lease with an expiry date and receives a fencing token, a number that increases every time the lease changes hands:

row = conn.execute(text("""
    INSERT INTO leases(resource_type, resource_id, owner_id, fencing_token, state, expires_at)
    VALUES ('Task', :resource, :owner, 1, 'ACTIVE', :expires)
    ON CONFLICT(resource_type, resource_id) DO UPDATE
    SET owner_id = EXCLUDED.owner_id, fencing_token = leases.fencing_token + 1,
        state = 'ACTIVE', expires_at = EXCLUDED.expires_at, updated_at = now()
    WHERE leases.expires_at <= :now OR leases.state IN ('EXPIRED', 'RELEASED', 'REVOKED')
    RETURNING fencing_token"""), {...}).first()
if row is None:
    raise DomainError(ErrorCode.LEASE_REQUIRED, "Resource already has a valid lease")

A single statement does all the work: if there's no lease, it creates one; if there's an expired or released one, it takes it and increments the token; if there's a valid one, it returns nothing and the acquisition fails. After that, every write checks that its token is still the current one. Picture this: a worker hangs, loses its lease and then "wakes up" with an old token. It can't write over the work of whoever replaced it. This is tested with two real threads competing against PostgreSQL, and only one gets the lease.

In the same transaction in which the task starts, the outbox events and the audit records are written too. Either everything is committed, or nothing is.

Lesson: in a system with workers that can die halfway through, a lock isn't enough; you need a token that proves you're still the owner at the moment of writing.

Versioned contracts

Everything that crosses a boundary has a versioned JSON Schema contract: an agent's invocation and its result, the approval request and decision, the receipt for an effect, the compensation request, the planner's proposal, the result of a reconciliation, the context manifest... Fifteen in total, all at version 1.0.0.

The context manifest ended up having a life outside the project. Its classification of reasons for excluding something from the context (for example, BUDGET_EXCEEDED as its own reason, distinct from "not relevant") is what Neon's context pruning uses today. Designing a contract well here paid off for something that didn't exist yet.

Six audits for one worker

The most demanding work package was the local worker's, the process that actually executes effects on the machine. It needed six rounds of external audit before passing, and each round raised the bar:

  • At first, completing an execution neither locked nor validated the task. The fix was to lock execution, task and lease in the same unit of work, with version comparison.
  • If the result of an effect is unknown, the system enters a "requires reconciliation" state and refuses to let another worker take over until it's reconciled. No blind retries.
  • The worker validates its own identity with a persistent latch that fails closed: it refuses to run as root, with kernel capabilities or without NoNewPrivs, and it rejects symbolic links anywhere along the trusted paths.
  • In the last round, every credential read from /proc had to match exactly the one the kernel returns for the current thread. Any missing, duplicated or divergent field leaves the latch closed.
  • And the tests prove what matters: if validation fails before acquiring, the task is left as it was, with no executions or leases; if it fails right before the effect, the effect never runs.

Lesson: when a component executes real effects, you have to revalidate right before acting and not just at the start. The world may have changed in between.

The cost of rigor

The other side has to be told too. With all this, JARVIS-PD moves slowly. Gate 0 is certified, phase 1 is only partly implemented, the LangGraph coordination package is waiting for review, and the next packages are defined but not authorized. There was a moment when I was lost with the project and asked for exactly the opposite: an unstable but working Jarvis, even if it meant sacrificing technicalities. Two days later, Saturno stopped being a script for a single task and became an autonomous daemon that works on its own.

Looking back, I think you need both. Saturno is where I explore, make mistakes quickly and find out what I really need (almost all the breakdown chapters come from there). JARVIS-PD is where what I already know I need gets built, so that it doesn't fail. The mistake would be to use JARVIS-PD's rigor to explore, or Saturno's speed for the core.

What I take away

  1. Agents propose, deterministic services materialize.
  2. Gates with concrete requirements and reproducible evidence, and a status vocabulary with no "almost".
  3. A gate that can fail finds what an eyeball review doesn't see.
  4. Don't simulate a path by writing to the database: if the path doesn't exist, the test proves nothing.
  5. Leases with fencing tokens when workers can die halfway through.
  6. Revalidate right before every effect and fail closed.
  7. Rigor for the core, speed for exploring, each in its own place.
