Putting a budget on a call before it goes out

A policy enforcement point in front of every model call: measure against actual usage, fail closed at every step, and why a control that validates one thing and sends another controls nothing.

JARVIS-PD · tokensBack to blog

In the chapter on Neon's cost, I described how one session ate 12 million tokens before anyone noticed. The safeguards I added there react during the session or after it. With JARVIS-PD I wanted to go one step further: no call to a model can go out unless it fits its budget, and any surprise in consumption blocks the system instead of going unnoticed. This chapter covers how I designed that piece, a policy enforcement point (PEP) in front of every call, and what I learned from actually measuring how many tokens get spent.

The underlying question: how many tokens will this cost?

To enforce a budget before the call, you have to know what the call will cost before making it. There were two options:

  • Policy A: estimate locally with a tokenizer. It's fast, free, and depends on no one.
  • Policy B: ask the provider through its counting endpoint, which counts tokens without generating anything, and only then make the real call. At most two contacts per run: one to count and one to generate.

I chose B out of caution, before having measured anything. Then I measured.

The measurement: the local tokenizer came in at a third

I made a single real call, expressly authorized (a minimal request to Codex asking it to reply "OK"), and compared the real usage with the local estimate:

  • Real usage according to the API: 14,861 input tokens.
  • Local estimate (the prompt rendered locally and counted with tiktoken): about 4,860.

The tokenizer came in at a third. The cause is that the local rendering didn't include the tool definitions that travel in the real request, and those definitions were most of the count. A budget calculated locally would have been three times too optimistic every time, which is exactly the failure the whole design is meant to prevent.

Another equally useful finding came out of it: the summary that the Codex CLI prints when it finishes ("tokens used: 3858") doesn't match the API's real usage. They are different metrics.

Lesson: before enforcing a budget, measure against the real usage the API returns, not against what your tokenizer estimates or what a CLI prints. The tools, schemas and system prompt you can't see are usually most of it.

What I couldn't validate, and why it didn't block me

I couldn't test the premise of Policy B, that the provider's pre-count matches what's later billed. There's no pay-per-use API key on this machine, only the subscription login, and using those credentials for the counting endpoint would have meant taking them outside their intended use. I didn't try.

This didn't hold up development, for a design reason: the system already had a safety net built for exactly this case. If the pre-count and the real usage diverge, the policy locks persistently. If the premise turns out to be false in production, the system fails closed and raises the alarm, instead of carrying on with a badly calculated budget.

The design: fail closed at every step

The flow of an invocation is short, and every step has a safe exit:

def invoke(self, request, sender):
    self._validate_static(request)                               # 1. reglas fijas
    input_hash = hashlib.sha256(request.sealed_input).hexdigest()
    self._reserve_invocation(request.invocation_id, input_hash)  # 2. idempotencia

    reserved_input = self._count_client.count(request)           # 3. contacto 1: contar
    if not isinstance(reserved_input, int) or isinstance(reserved_input, bool) or reserved_input < 0:
        self._block_policy("COUNT_RESULT_INVALID")
        raise DomainError(ErrorCode.PRECONDITION_FAILED, "COUNT_RESULT_INVALID")
    if reserved_input + request.max_output_tokens > self._policy.token_budget_total:
        raise DomainError(ErrorCode.PRECONDITION_FAILED, "TOKEN_BUDGET_EXCEEDED")

    response = sender(request)                                   # 4. contacto 2: generar
    usage = self._parse_usage(response)
    self._verify_postflight(request, reserved_input, usage)      # 5. comparar
    self._complete_invocation(request.invocation_id, usage)
    return usage
  1. Fixed rules. Policy version, runtime digest and version, exact model, identity of the counting endpoint, a non-empty sealed input, no tools, no skills, no history, no fallbacks, no extended reasoning mode, and an explicit output limit that doesn't exceed the policy's. If anything doesn't add up, nobody gets contacted.
  2. Idempotency. Each invocation reserves its identifier in PostgreSQL before talking to the provider. If anything fails from here on (a timeout, a network error), the reservation stays "in progress" forever and that identifier can't be retried. That's inconvenient on purpose: a silent retry is exactly how a cost gets duplicated.
  3. Budget before generating. The reserved input tokens plus the output limit have to fit within the policy total.
  4. A single generation.
  5. Post-check. If the model that responded isn't the expected one, if there was more than one attempt, if the real input deviates from the count by more than the tolerance, or if the output exceeded the limit, the entire policy locks persistently until someone reviews it.

I didn't delegate the concurrency guarantee of the reservation (that two requests with the same identifier can't both get through). Because it was so critical, the reviewer model wrote it and verified it directly, with a real race of 5 threads on the same identifier. Exactly one won, through real row locking and not a simulated one.

A local estimator, but only where it's reliable

Without a paid key there was no counting endpoint, so a local counter was needed. What's interesting is why it was viable here, when the measurement said the tokenizer came in at a third. The underestimate came from the tools, skills and history that travel in the real request, and the fixed rules in step 1 already reject any request that carries them. For the only thing this policy lets through, the sealed input is the entire payload, so counting it directly should come much closer.

Even so, "much closer" still isn't exact, so I added a tolerance margin to the policy. By default it's zero, which is correct with an authoritative counter, and it can be widened with a measured margin when an estimator is used. The estimator is still uncalibrated against real usage, and it's written down that way.

Lesson: an estimator that fails in general can be reliable in a narrow case if your own rules eliminate what made it fail. But it's still an estimator: give it an explicit margin and don't treat it as truth.

From prototype to runner: "MVP achieved" without having run it

Codex wrote the HTTP runner that puts this PEP in front of the real calls and reported that the MVP was achieved, with tests, ruff and mypy all green and a "demonstration" document. But the document was instructions for running it, not evidence that it had been run. Nothing had been executed. The first real request exposed three bugs, and testing by hand turned up two more:

  1. The forwarding URL had /v1 duplicated.
  2. It expected a normal JSON response, but the Responses API returns an SSE stream.
  3. A unit-of-work factory that was wrapped twice raised a TypeError on the first invocation.
  4. The output limit the client sent was replaced by the policy's for the check, but the body forwarded to the provider still carried the client's original value. In other words, the budget was checked with one number and spent with another.
  5. The 403 only exposed the generic error code, not the specific reason for the rejection.

The fourth is the most serious: a budget control that validates one thing and sends another controls nothing, and on top of that it raises no error. I fixed all five and verified them again by hand against the real system, and this time the demonstration was saved as captured evidence: a real request that passes through the policy and reaches the model, one with too many output tokens rejected before contacting anyone, and one whose input already exceeds the budget, rejected all the same and with its identifier blocked forever.

Lesson: at a control point, what gets validated and what gets sent have to be literally the same object. And a "it works" without a captured execution isn't evidence, it's a promise.

A wrong conclusion drawn from real code

To connect the runner to OpenClaw, I needed to know whether its configuration decides which provider the main model uses. Codex's first attempt failed silently because of the sandbox: it couldn't access Docker, and it reported that as a real permissions problem. The second one did read actual code, but drew an incorrect conclusion: it saw that one part of OpenClaw only reads the provider configuration for a review subsystem and generalized that to "the configuration doesn't affect the main model".

Reading the function that resolves the provider, and its call, directly, the reality was different. For agents without an explicit override, OpenClaw doesn't send any provider when starting the thread, so the Codex binary is free to resolve it from its own configuration. These were two independent facts, and they had been mixed together. Even so, I noted it as not verified end to end, because reading code isn't the same as starting a real thread with the configuration changed.

Lesson: an agent having read real code doesn't make its conclusion correct. When the conclusion is a generalization ("this doesn't affect that"), look for the exact point in the code that would support it.

What I take away

  1. Budget before the call, don't just watch afterwards.
  2. Measure against the real usage: local tokenizers and CLIs can come in at a third.
  3. Fail closed: no silent retries, with single-use identifiers and persistent lockout on any deviation.
  4. An estimator only where your rules make it reliable, and always with an explicit margin.
  5. What gets validated and what gets sent, the same object.
  6. Captured evidence, not instructions, and conclusions backed by the exact point in the code.
