Let Neon talk and let someone else do the work

Neon stopped executing commands and started delegating: a background agent for new tasks and an HTTP bridge to my Claude Code sessions in tmux. The architecture, and what was learned while wiring it up.

Neon · architectureBack to blog

For weeks Neon did everything: it talked to me, decided what I wanted, and also did the work, running shell commands from its own voice turn. It worked, but it had three problems that turned out to be the same one. The voice turn got blocked while a long command ran. Every command output went into the context and was paid for on every following call (the chapter on cost covers how far that can go). And on top of that, I was paying API prices for an expensive model to do tasks that a coding agent, using the subscription I already pay for, does better. Adding the Claude Code subscription, monthly spending was getting close to €80 for a personal project.

After turning it over for a while, the idea is simple to state: separate the conversation from the execution. Neon only talks, and someone else does the work. In this chapter I explain how I set it up and, above all, the problems that showed up when I connected the pieces.

The architecture

                   ┌──────────────────────────────────────────────┐
  voz ──► Neon ────┤ dispatch_task ──► task_runner (claude -p)     │──► Telegram
 (Haiku,           │                    proceso aparte, systemd    │──► aviso en la llamada
  sin shell)       │                                               │
                   │ resume_agent_session ──► puente HTTP ──► tmux │──► sesiones de Claude Code
                   └──────────────────────────────────────────────┘     que ya tengo abiertas
  • Neon is only the conversational layer. It runs on Haiku, a cheaper model, and its system prompt says explicitly that its role is to talk to me and that it delegates everything that isn't conversation.
  • Neon no longer has a shell. I removed the tool for running commands, because a model that only converses shouldn't be able to touch the system.
  • Two paths for the work: new tasks, which launch a background agent, or instructions for Claude Code sessions I already have open in tmux, which have their own working context (the trading bot, the blog...).

Delegating without blocking the turn

When I ask for something that takes several steps ("research this", "fix that"), Neon calls dispatch_task. That tool writes the task to a file, launches the agent as a transient systemd unit, decoupled from Neon's process, and returns a task_id immediately. systemd-run returns as soon as it registers the unit, not when the work finishes, so the voice turn stays free and I can keep talking.

proc = await asyncio.create_subprocess_exec(
    "/usr/bin/systemd-run", "--user", f"--unit=neon-task-{task_id}",
    "/usr/bin/python3", str(RUNNER_SCRIPT), task_id, str(task_file), str(status_file), project_path,
)

The background agent is claude -p in autonomous mode, using my subscription session and not the API. It has a one-hour timeout and it's the only real path to the machine: if root is needed, it goes through one specific wrapper script that sudoers allows, and nothing else. Back when Neon ran commands itself, it asked me for spoken confirmation before doing anything destructive. In the background there's nobody listening to confirm anything, so I moved those rules into the background agent's prompt: don't claim something was done if it wasn't, and never take irreversible actions without permission.

The result is capped at 2,000 characters, and the agent writes it already meant to be read aloud: no markdown, no tables, no unnecessary jargon. When it finishes, it notifies me through two channels at once. One is a direct Telegram message, which doesn't spend a single Neon token. The other is a marker on disk that Neon checks while a call is open, so it can tell me about it with the polite check-in from the Neon chapter.

Lesson: if a conversational agent has to wait for the work to finish, it isn't conversational. Delegation has to hand control back immediately and notify afterwards through a channel that doesn't cost conversation.

The bridge to the tmux sessions

The second path is the more interesting one. I work with several Claude Code sessions open in tmux, each with its own context: one for the trading bot, another for the blog, another for Neon's development... What I wanted was to tell Neon "tell the trader session to look at such-and-such" and have the instruction arrive there, without Neon doing the work itself. What Neon pays for is a cheap HTTP call; the real work is paid for by the other session, which is already running on the subscription.

The complication came from where each piece lives. I set up a copy of Neon inside an Incus container to try the new architecture without touching the original, but my sessions have to stay on the host because they depend on things on the host. The container is unprivileged and remaps UIDs: a process that is called neon inside is, to the host, a different unprivileged UID, and it can't open my user's tmux socket. The simplest way to cross that boundary was a small HTTP service, authenticated with a token, that runs natively on the host and that the container calls over the Incus bridge network.

Building it taught me several things.

The Enter that only added a line break

The first test seemed to work: Neon opened the session, the message appeared typed into Claude Code's input box... and stayed there. Enter only added a line break. When I sent the text and the Enter in the same tmux send-keys call, or too close together, Claude Code's interface interpreted the whole burst as a paste. The standard fix is to split them into two calls with a real pause in between, so the text registers as typed before the Enter arrives as a separate keypress.

subprocess.run(["tmux", "-S", TMUX_SOCKET, "send-keys", "-t", session, text], timeout=10)
await asyncio.sleep(0.3)   # que el TUI registre el texto como tecleado
subprocess.run(["tmux", "-S", TMUX_SOCKET, "send-keys", "-t", session, "Enter"], timeout=10)

An API, not a screen

The first version gave Neon the raw dump of the tmux screen and asked it to summarize what it saw. Bad idea, for two reasons. It burned tokens interpreting borders, keyboard shortcuts and spinners that mean nothing when read aloud. And, worse, it pushed Neon into doing the work itself instead of just passing on the message, exactly what I was trying to avoid, spending API money on something that has nothing to do with being a voice assistant. I replaced it with a proper API: /send sends the message and /reply returns a clean answer or "still working". The screen parsing happens once, in the bridge, and Neon never sees tmux.

Knowing where the answer starts

To know which part of the screen is the answer, the bridge stored how many lines there were when the message was sent and compared that with a later capture. That isn't reliable: two separate capture-pane captures don't have to match in line count. I confirmed it with a real failure in a test where the answer "LISTO" was already on screen and /reply kept saying "working". Now the bridge anchors on the text that was sent, looking for it in the new capture, instead of on a remembered number.

Less clever, more correct

To keep only "the answer", the bridge filtered for lines starting with the ● marker that Claude Code uses. With one-line answers ("PERFECTO") it worked, but in a multi-paragraph answer the marker only appears on the first line of each paragraph, and the rest was silently lost: long answers arrived empty or cut off. Now /reply returns the whole block between the sent message and the end marker. It's less clever and more correct. And I added /history to pull the session's full history, instead of having the bridge guess how much context is enough.

The list that had to be maintained by hand

At first the bridge had a fixed list of valid sessions. Every time I created a new session, Neon told me I had to add it to its list. The first fix made the check dynamic in the bridge, but I forgot that Neon's tool had its own fixed list in the schema, so the model couldn't even name a new session. Now the bridge is the single source of truth: any tmux session that is running claude is valid, and it's checked on every call.

Lesson: at a boundary between systems, every copy of the same rule (a list of sessions, a response format) is one more place where it can go stale. Put it on one side and have the other side ask.

What's still pending

Not everything is finished. The full idea includes letting the background agent switch engines dynamically, from Claude Code to Kimi Code, when it hits my account's session limit. The first test with Kimi Code never got as far as evaluating anything: it started in manual approval mode (asking permission for every ls), and once I sorted that out, the Kimi Code product's gateway cut the task off at a limit of 3 requests per minute before it touched any code. The automatic engine switch is already written, right at the point where the agent detects the session limit, but until I have Kimi paid for and logged in, it fails silently and the task ends with the usual limit error.

What I take away

  1. Separate conversation from execution. The model that talks to you doesn't have to be the one that works, or the most expensive one.
  2. Take the hands off the one that converses. A model that only converses shouldn't be able to touch the system; access to the machine goes through a single path.
  3. Delegating means handing control back immediately and notifying afterwards through a cheap channel.
  4. Give the agent an API, not a screen. If you give it raw information it has to interpret, it will end up doing the work itself.
  5. At boundaries, a single source of truth, and solid anchors (the sent text) instead of fragile assumptions (a line count).
  6. Less clever, more correct: clever filters fail silently on the cases you didn't see.
